# AI 助理使用經驗報告（捲字 JuanGo 開發）

整理自這個專案 `SUMMARY.md`、`MEMORY.md` 裡 2026-11-23 一天內的 Dia Cowork 任務紀錄（約 20 個任務代號）。只寫紀錄裡真的發生過的事。

## 一、使用情況

**工作方式**：AI 助理在 Dia 瀏覽器裡，透過 Vorssaint 在 Mac 上跑終端機指令。每次只在專案的隔離副本（`捲字 JuanGo 開發版_tmp`）裡改檔，改好、驗證過，再由使用者決定要不要覆蓋原資料夾。每個任務留下 PLAN.md（待辦＋驗證方法）、MEMORY.md（決定與原因）、SUMMARY.md（跨任務接續）。

**做過的事（依類型）**：

| 類型 | 具體例子（任務代號） |
| --- | --- |
| App 功能 | 對戰房間改版：等候室、準備／開始、請離開、邀請好友（DC-2F9B87AF）；邀請在對戰首頁也會跳出（DC-A8673FFB）；邀請輪詢 10 秒改 2 秒、確認窗統一用 alert（DC-953F3DB7） |

## 二、挑戰與解決方法

| 挑戰 | 實際情況 | 解決方法 | 可參考的做法 |
| --- | --- | --- | --- |
| 重跑舊 SQL 把線上設定改回去 | 重跑 `battle_ranked.sql` 收回所有 battle_* 函式權限，好友列表壞掉；同一件事也讓電腦從排行消失、配對分數亂掉 | 新增可重跑的 `supabase/battle_grants.sql`，SQL 檔開頭寫明重跑順序，檢查查詢最後輸出 true/false（DC-241D8F5F、DC-AAC4982F） | 每個 SQL 檔都做成可重跑，最後附一段「檢查結果」；兩個檔案定義同一個函式時要保持同一版（本次的 `report_word` 也照這樣做） |
| AI 不能替使用者動正式資料庫 | 所有 SQL 都要使用者自己在 Supabase SQL Editor 執行 | AI 只寫檔、寫好執行順序和檢查查詢，摘要裡列待辦 | 待辦寫進 SUMMARY.md，下次任務開頭先看，不會忘 |
| 裝置不一定連得上 | iPhone 16 Pro 某次 unavailable、BlueStacks 某次沒連線、`adb` 不在 PATH | 改裝另一支 iPhone；用 BlueStacks 內建的 `hd-adb`；沒裝到就照實寫進摘要 | 裝置 ID、adb 路徑記在 MEMORY.md |
| 只看程式碼猜畫面會猜錯 | 返回鍵位置、官網排版都是截圖才看出問題 | 規定顯示問題先截圖再改、改完再截圖對照 | 本次返回鍵修好後也是截 BlueStacks 確認 |
| release 版才出現的錯 | Android 正式版課文書架辨識 NullPointerException，debug 版正常 | 查出是 R8 縮減掉 ML Kit 類別，加 keep 規則（DC-ADB05CF6 發現，本次正式修進 `app/tool/prepare_android.sh`） | 改產生檔要改「產生它的腳本」，不然下次重新產生就不見 |
| 工具有自己的限制 | Dia 瀏覽器工具開不了 localhost；headless 截圖手機畫面是黑的 | 請使用者自己打開確認，摘要裡註明「AI 沒看過畫面」 | 看不到就說看不到，不假裝確認過 |
| 指令輸出太長被截斷 | 一次跑太多步驟，回報中間被省略 | 輸出導到 log 檔，只 grep 關鍵行 | 一個區塊只驗證一件事 |
| 使用者一句話意思不清 | 「重來」「繼續」「這排版都一樣啊」 | 先問一題選擇題再動手（例如本次問要做哪幾件） | 問「要做哪一件」比猜錯重做省時間 |
| 對話中斷、要接續 | 網路斷線、上一個對話沒回報 | SUMMARY.md 每次寫「下次接續」 | 新對話只要讀 SUMMARY.md 就能接上 |

## 三、總體感受

**做得好的地方**
- 速度：一天內完成功能、後台除錯、文件、官網、實機安裝，多數改動都有 flutter test（97–98 項）或 xcodebuild 驗證。
- 可追溯：每個決定都有原因寫在 MEMORY.md，回頭查「為什麼這樣改」找得到。
- 安全邊界清楚：只改副本、正式資料庫和登入操作都留給使用者，覆蓋原資料夾前會先問。

**限制與成本**
- 正式資料庫、App Store／Play 後台、實機手勢操作都要人來做，AI 只能準備好步驟。
- 同一個問題（重跑 SQL 把設定改回去）出現了不只一次，代表「說明怎麼避免」不夠，要做成檢查（例如檢查查詢、build 失敗）才可靠。本次發版金鑰也是這個思路：沒有金鑰就讓 release 建置直接失敗。
- 指令要一步一步等回報，大建置一次要 1–5 分鐘，來回次數多時整體偏慢。
- 測試多是編譯和單元測試，兩支手機互邀、真實拍照辨識這類流程還是要實機自己測。

**結論**：適合當「會動手的協作者」：查原因、改程式、寫文件、做驗證都很快，而且留下的紀錄讓下次能接著做。但上線前的最後一步（執行正式 SQL、實機測試、保管金鑰）仍要使用者自己確認。
